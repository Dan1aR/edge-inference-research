# E6. Аппаратная сторона BF16-аккумуляции: подсчёт MAC, доля FP32-аккумуляции, модель стоимости, синтез

Отвечает на замечания рецензентов: «claimed hardware benefits are not demonstrated» и «какая доля
32-битных операций и ресурсов остаётся в смешанном режиме (FP32-аккумуляция только в attention, BF16
в остальном)». NPU у нас нет. Всё ниже посчитано на CPU: аналитически, инструментированием
реального forward-прохода, аналитической моделью энергии/памяти и логическим синтезом открытыми
инструментами. **Энергия и память — это оценки модели, а не измерения на кремнии.** Площади взяты из
логического синтеза (без размещения и трассировки).

Воспроизведение: `scripts/hw/run_all.sh` (только CPU, `nice -n 19`, не больше 2 процессов, около 1.5 мин).
Сырые числа лежат в `results/hw/*.json`, таблицы печатает `scripts/hw/make_tables.py`.

## 1. Подсчёт MAC (вход 512×512, batch 1)

Геометрию проверили по HF-конфигам. Обе модели: patch 16, 12 слоёв, `num_detection_tokens = 100`,
d_h = 64, 91+1 класс. Токенов N = 1 (CLS) + 32·32 (патчи) + 100 (детекционные) = **1125**.
yolos-tiny: d = 192, 3 головы, d_ff = 768. yolos-small: d = 384, 6 голов, d_ff = 1536,
`use_mid_position_embeddings = true`.

Компоненты совпадают с флагами `src/run_experiment.py`. `patch` соответствует флагу patch. `qkv`,
`attn_out`, `mlp` и `head` — это все `nn.Linear`, флаг lin. `qk` и `av` — матмулы внутри
`YolosSelfAttention`, флаг attn. «Выходы» — число результатов аккумуляции, то есть элементов выходной
матрицы GEMM. K — длина редукции.

Как проверяли. (a) Аналитическая формула по конфигу. (b) `TorchDispatchMode` на реальном CPU
forward (`attn_implementation="eager"`) записывает каждый aten `mm/addmm/bmm/convolution` вместе с
модулем, который его вызвал. (c) Независимо от этого — `torch.utils.flop_counter.FlopCounterMode`,
FLOPs/2, на eager-пути и на sdpa-пути (math backend). **Все три подсчёта совпали до одного MAC**,
скрипт это проверяет через `assert`. Одна деталь: fused CPU flash-SDPA FlopCounter не учитывает
(без принудительного math backend он теряет 5.83 GMAC у tiny), поэтому для sdpa используется math backend.

Не учтены (не являются MAC в GEMM): bias, LayerNorm, GELU/ReLU, softmax, масштаб 1/√d_h,
residual, бикубическая интерполяция position embeddings (для фиксированного 512×512 её можно
посчитать один раз заранее).

## 3. Аналитическая модель стоимости (ОЦЕНКА)

**Энергия арифметики на MAC.** Источник: M. Horowitz, «Computing's energy problem (and what we can do
about it)», ISSCC 2014, 45 нм, 0.9 В. Табличные значения: FP add 16 бит 0.4 pJ, 32 бит 0.9 pJ;
FP mult 16 бит 1.1 pJ, 32 бит 3.7 pJ. Произведение bf16×bf16 точно представимо в FP32 (значащие
8×8 = 16 бит ≤ 24), поэтому:
- MAC «BF16-in / FP32-acc» = 16-битный умножитель + 32-битный сумматор = 1.1 + 0.9 = **2.0 pJ**;
- MAC «BF16-acc» = 16-битный умножитель + 16-битный сумматор = 1.1 + 0.4 = **1.5 pJ** (×0.75).

Вариант «bf16-mult». У Horowitz 16-битный FP — это fp16 с 11-битной мантиссой, а у bf16 мантисса
8-битная. Энергию умножителя масштабируем на (8/11)² и получаем 0.58 pJ: 1.48 против 0.98 pJ (×0.663).

Энергия режима: E/E_B = [s·e₃₂ + (1−s)·e₁₆]/e₃₂, где s — доля FP32-acc MAC. Абсолютные числа для
B: 23.9 мДж на инференс у tiny и 71.8 мДж у small. Это только арифметика: без SRAM/DRAM операндов,
управления и интерконнекта, поэтому относительный выигрыш на уровне всего чипа будет меньше.

Столбец «площадь (синтез)» — прокси из раздела 4: s + (1−s)·0.595, где 0.595 — отношение
комбинационной площади PE `bf16acc_sep` к `fp32acc_sep` на Nangate45. Его можно читать двумя
способами. (а) Грубая оценка энергии, пропорциональной площади. (б) Площадь гетерогенного ускорителя,
сбалансированного по пропускной способности: основной массив на BF16-acc плюс отдельный FP32-acc
блок под долю s.

**Хранение partial sums** (`cost_model.py`, параметры задаются):
- **Output-stationary R×C массив.** Один аккумулятор на PE, 32 бита против 16. Для 32×32 это 4 КиБ
  против 2 КиБ, для 128×128 — 64 КиБ против 32 КиБ. Важно: **в однородном массиве любой смешанный
  режим (M1, M2, …) требует 32-битных аккумуляторов во всех PE, то есть 100% регистров B.** Экономия
  регистров и площади появляется только при гетерогенной архитектуре или PE с режимом «1×FP32 / 2×BF16
  lane». Последний вариант мы не синтезировали.
- **psum-байт.** Объём результатов аккумуляции в разрядности аккумулятора (4 Б или 2 Б на выход).
  Это имеет значение, если partial sums уходят в буфер или память.
- **split-K spill.** Если K больше K-тайла T, каждый выход пишется и читается обратно ceil(K/T)−1 раз.
  При T = 128 это касается только patch, mlp.output и av (K = 768 / 768 / 1125). В B у tiny это
  423 МиБ на инференс (около 1.1 мДж при 20 pJ на 64 бит из 32 КБ SRAM), при T = 64 — 888 МиБ,
  при T = 256 — 122 МиБ.
- **Weight-stationary R×R (как в TPU).** K раскладывается по строкам, каждый выход получает ceil(K/R)
  read-modify-write в accumulator SRAM. В B у tiny это 2.6 ГиБ на инференс для 32×32 (около 3.4 мДж
  при 10 pJ на 64 бит из 8 КБ SRAM) и 0.70 ГиБ для 128×128.

Для M1 трафик partial sums падает только до 0.69–0.75 от B. Причина в том, что av, у которого самая
длинная редукция, остаётся в FP32. M2 (0.62–0.69) по трафику не лучше M1 при split-K, но лучше в WS.

## 4. Синтез (открытые инструменты)

**Маршрут.** RTL — `scripts/hw/rtl/mac_units.v` поверх Berkeley HardFloat Release 1 (Verilog,
recoded-формат, RISC-V NaN), режим округления RNE зафиксирован константой, полная IEEE-семантика
(субнормали, Inf, NaN). Синтез — Yosys 0.70 (`yowasp-yosys`, сборка WebAssembly, без системной
установки). Сначала `synth -flatten` даёт счёт generic-вентилей. Затем
`dfflibmap` + `abc -liberty` на двух библиотеках: **NangateOpenCellLibrary typical (FreePDK45, 45 нм —
тот же узел, что у Horowitz)** и **sky130_fd_sc_hd tt_025C_1v80 (130 нм)**, обе из
OpenROAD-flow-scripts.

**Блоки:**
- `mul_bf16_exact_fp32` — точное произведение bf16×bf16 → fp32: `mulRecFNToFullRaw(8,8)` + перевод в fp32;
- `add_fp32` / `add_bf16` — `addRecFN(8,24)` / `addRecFN(8,8)`;
- `mul_bf16` — округление произведения до bf16;
- `fma_*` — `mulAddRecFN`, фьюзный вариант;
- `pe_*` — PE для output-stationary массива: два 17-битных регистра проброса операндов, регистр
  аккумулятора на 33 или 17 бит (recoded-формат), сигнал clr;
- `pe_bf16acc_sep` по численной схеме совпадает с `src/bf16_accum.py`: произведение округляется до
  bf16, затем сложение в bf16.

**Функциональная проверка.** Синтезированные gate-level нетлисты восьми тестовых обёрток (стандартный
IEEE на входе и выходе) прогнаны побитово-параллельным симулятором на Python на 4000 случайных
векторах каждая. Векторы включают точное сокращение, разности экспонент до ±30 и нули. Эталон —
битово-точный numpy RNE. **Все 8 обёрток: 0 расхождений.**

**Найденный баг HardFloat.** Проверка поймала ошибку `addRecFN` при sigWidth = 8 (bf16):
`alignDistWidth = clog2(sigWidth) = 3`, поэтому максимальный сдвиг выравнивания равен 7. Операнды с
разностью экспонент ≥ 8 выравниваются неверно. Без исправления 2525 из 4000 сложений bf16 неверны,
например −51.25 + 0.0187 → −51.0 (`results/hw/synthesis_unpatched_hardfloat.json`). В копии,
собираемой для синтеза, применяется патч `clog2(sigWidth + 3)`. Для sigWidth = 11/24/53/113 он ничего
не меняет: площадь `add_fp32` та же, fp32-тесты проходят до и после. Для bf16 он расширяет сдвигатель
до 4 бит. Исходники HardFloat не меняются.

По синтезу выходит, что MAC с FP32-аккумуляцией в 1.6–1.9 раза больше по площади, чем MAC с
BF16-аккумуляцией. В таблице Horowitz та же разница по энергии — 1.33×. Основная причина — сумматор:
при bf16-входах умножитель маленький (8×8), а FP32-сумматор в 2.45 раза больше BF16-сумматора и
доминирует. Значит, оценка ×0.75 по Horowitz скорее консервативна (без bf16-поправки ×0.66, по площади
×0.6).

## 5. Допущения и ограничения

1. Энергия — аналитическая модель по табличным данным 45 нм (Horowitz 2014). Учтены только арифметика
   и, отдельно, SRAM-трафик partial sums. Не учтены операнды из SRAM/DRAM, управление, интерконнект,
   leakage, glitch. Мощность синтезированных блоков не моделировалась: нет switching activity.
2. Синтез только логический. Нет placement/routing, wire load, timing closure и конвейеризации.
   ABC в `yowasp-yosys` не выдаёт отчёт о задержке, а `-D` на результат не повлиял, поэтому частоту не
   заявляем. Площади получены area-oriented маппингом, абсолютные мкм² занижены по сравнению с
   P&R-результатом. Отношения между двумя библиотеками стабильны (±4%).
3. HardFloat работает в recoded-формате (+1 бит экспоненты) с полной IEEE-семантикой. Ускорители
   часто сбрасывают субнормали (FTZ) и не держат флаги исключений, оба варианта стали бы меньше. Для
   bf16 нужен описанный выше патч `addRecFN`.
4. Модель режимов предполагает, что «смешанный» выигрыш реализуется гетерогенно (отдельный FP32-acc
   блок под долю s) или точностно-конфигурируемым PE. В однородном массиве с FP32-аккумуляторами M1 и
   M2 сохраняют 100% площади и регистров B; выигрыш по энергии тогда возможен только при гейтинге
   младших разрядов. Это мы не моделировали.
5. Доли MAC и выходов посчитаны для batch 1 и 512×512. Они не зависят от batch. От разрешения зависят:
   attention растёт квадратично по N.
